### 2.1 开发实践：TDD 分层打法（2026-08-18 增补）

TDD 按「红-绿循环成本」分层适用，**不是全域套用**：

| 对象 | 打法 | 理由 |
|---|---|---|
| L0 纯函数（D3 时间对齐 / D4 闸门 / D9 策略评估） | **严格 TDD**（先写测试→红→实现→绿→重构）+ **属性测试**（jqwik，见下） | 无 DB/网络依赖，循环毫秒级；D9 的甲/乙/丙/丁候选本身就是现成的参数化用例表 |
| L1/L2 集成与契约（D1 reader / D2 管理表 / D8 流水账 / D9 策略参数表 / L2 manifest 断言） | **契约先行**：断言批量先写、实现完成后跑——非逐步红绿 | 直连 10.0.0.9 网络往返使红绿循环变慢；manifest 断言天然是"先有的期望" |
| D5/D7 RuoYi 代码生成 CRUD 骨架 | **不 TDD**，补验收断言即可（值域校验/缓存生效等业务断言除外——那些照 L0/L1 打法写） | 测框架生成物无意义 |
| S1 判定真实现（**已解封**，2026-08-22 算法定稿） | **契约先行**（§4.2）——manifest oracle 在定稿后已是"正确的测试"，非逐步红绿；其纯函数子组件（`VTargetDecoder`/`EnvelopeAggregator`）照 L0 行严格 TDD + 属性测试（§5.0）；Stub 档契约形状已验（D9） | 定稿前无"正确的测试"的搁置理由已解除；judge 本体断言天然是"先有的期望"（manifest 映射） |

**TDD 起手式 = D3**（首个红绿循环对象，最干净）：属性断言（jqwik）先写、边界示例作锚点用例补充：

- **幂等**：`round(round(t)) = round(t)`——v5.0 §5「双重取整无害」契约的机器验证；
- **单调**：`t₁ ≤ t₂ ⇒ round(t₁) ≤ round(t₂)`；
- **值域**：`round(t)` 秒/毫秒位归零（结果对齐到整分钟），秒 ≥30 时向分钟进位正确（含 59 分跨小时进位）；
- 锚点：`29.999s` 舍 / `30.000s` 进 / 跨分跨小时跨天（示例枚不完的边界由属性生成器替你枚）。

**三个互补技术**（对示例式 TDD 的增强，非替代）：

1. **属性测试（jqwik，随 D3 引入）**：断言**不变量**而非个例，框架自动生成上千输入轰边界——D3（时间）、D4（正则闸门：合法格式恒通过、非法格式恒拦截且不抛）、D9（策略评估：同输入同配置输出恒定；任一输入在任一配置下恰好落一个处置桶——输入空间显式定义见 §4.8）三处受益。解码的「编码→解码往返可逆」属性随 S1 纯函数子组件 TDD 落地（目标值形态可逆；增量形态改「同输入同 t₀ 输出恒定」确定性属性——÷t₀ 后不可逆推原编码；Python `decode.py` 侧为既有 pytest 单测）。
2. **差分测试（两套独立实现同输入比对）**：① Java source 层 vs `verify/run_verify.py`（路 A，L4 既有）；② Python `decode.py`（契约级参考实现）vs Java judge 内解码——**随 S1 解封补**，届时对同一批 `warn_info` 原文两侧解码逐条比对。手写测试抓"想到的错"，差分抓"两个实现理解不一致"——口径反复变的项目里后者最危险。
3. **变异测试（PIT，首次评估 + 条件复跑）**：D9 策略纯函数落地后跑首次——往代码注入变异（改边界、翻条件），看甲乙丙丁参数化测试能否杀死，检验护栏是真还是摆设；**复跑触发 = 策略纯函数逻辑实质性变更**（如 S5 应用阶段调整处置逻辑；2026-08-19 评审吸收——否则评估结论随代码漂移过期且无提醒），不作常驻门禁；Maven 插件接入（§7）。

**通用原则（2026-08-19 评审提炼，本方案两处已用）**：能用类型系统 / DB 约束**结构性排除**的缺陷，不用测试逻辑去堵——§4.8 sealed 不相交并（编译期排除不可达组合）、§4.7 uk 生成列候选（DB 层排除 TOCTOU 竞态）皆此式。**边界（同日评审补正）**：原则只对**编译期 / DB 约束层**成立；**构造期/运行时校验代码**（如 §4.8 compact constructor 不变式）本身是逻辑、可能有 bug（⟺ 误写单向、条件写反），**须照 L0 严格 TDD 测它**——「类型堵」堵的是消费方误读，校验逻辑自身的正确性仍是测试的活。

**前置**：在 L2 真实现档跑 manifest oracle 断言前，§6 前置差距（thresholds.yaml 旧值 + manifest 重算）必须先收口——否则断言对的是**假期望**（该档是契约先行、非逐步红绿，见上表）。（✅ thresholds.yaml 部分已收口 2026-08-22：窗口参数对齐 D7 锁定值并重灌，见 D9 报告 §八；其余 §6 项随回放收口。）

### 4.2 L2 契约测试 · RegulationJudge + manifest 映射（D9 骨架 / S1 真实现共用）

参数化契约测试（**19 个调节场景 S01–S19** × manifest 期望；U01–U07 投运率场景不经 `RegulationJudge`，不进本契约测试，随 S 轨另设）。**分两档跑，断言代码同一批、零改动**：

- **Stub 档（现在）**：`StubRegulationJudge` 只验**契约形状**——`RegulationOutcome` 类型可构造/可序列化、`stub=true` 标记在、确定性/非随机（下条 bullet）。**Stub 不可能满足 manifest 期望**（S02 期望 PEN 等），期望断言此档**跳过**——v5.0 §8.2 对 stub 的定位就是"能编译、能调通、有返回值，不保证正确"。
- **真实现档（S1 解封后）**：换 Bean 指向 `DefaultRegulationJudge`，同一批参数化断言按映射表全量生效——**准入门槛 = 19 场景全量通过**。

v5.0 契约是两态 + Undecodable，manifest 是三态时代产物，**期望映射表**：

| manifest 期望 | v5.0 断言 |
|---|---|
| `QUAL`（快/经各档） | `Judged` 且该档 `VERDICT=QUALIFIED` |

### 4.8 D9 · 类型化失败契约 + 参数化策略骨架（L0，v5.0 新增）——✅ 已落地（L0 53 + L1 15，报告 D9）

### 5.1 上线前置：真实数据回放验收（2026-08-19 增补，Leo 拍板写入）

> 来源：外部评审 III 建议——合成测试库跑通 ≠ 真实数据正确性（循环码轮转、越限分支、点号真实语义均未经生产数据检验，见 CLAUDE.md Open follow-ups）。**正式上线前必须完成一轮真实数据回放：**

1. **回放对象**：向对端 AVC 系统取一段历史真实数据——`warn_info` 指令 + 对应窗口 `his_curve_sv` + 门控/并网/退出原因/免考 yx 点，覆盖目标值与增量两种指令形态、含越限指令、含缺数据时段。
2. **回放动作**：真实现 `DefaultRegulationJudge`（S1 解封后）+ 统计管线全链路跑该段数据，产出逐指令两档结论 + 免考应用 + undecodable 归因。
3. **人工抽查门槛**：随机抽几十条（建议 ≥30）指令人工核对——对照 `warn_info` 原文手算 `V_target`、手查窗口极值，核对两档结论/免考应用/归因，全对才过；发现错判 → 回归修判定/解码后重跑。
4. **归属与留痕**：阶段 6（S1 循环码定稿）之后、阶段 7（统计上线）之前执行；抽查记录留档（谁抽、抽了哪些、结论）。`t_fast` 默认值（正式版 §2.4.1 待定建议 4）在本轮回放中一并复核确认。
5. **顺带量化「判不了」真实占比**（2026-08-19 评审 IV 补）：回放数据全量统计 undecodable / 缺数据 / 数据无效占比——合成库的失败场景（S12/S14/S16 等）是人为构造、占比自造，**对真实占比无指示意义**；真实占比是 #3/#5 策略拍板（宽松跳过 vs 阈值剔除 vs 计不合格）的关键输入，偏高则策略定稿升优先级。
6. **数据可提前索取**：回放所需真实数据段可**现在就向对端发起索取**（不阻塞 D1~D9 确定轨推进），到手后先做人工预读（编码形态、循环码轮转、信号抖动表现、对端信号质量迹象——并网/退出原因/免考旗有无冻结或异常，为策略文档 §6-6 信号校验方案提供现实依据），为 S1 解封与回放做准备（2026-08-19 评审 IV 补；风险矩阵对照版 8-19 增）。

## 6. ⚠️ 前置差距（开工 D9 / S1 契约测试前必须收口）

> 这是本次盘点新发现的问题，**阻塞 manifest 作为 oracle 的有效性**：

1. **`thresholds.yaml` 是拍板前旧值**：`t_fast_min: 5`、`t_econ_min: 30`（注释还写着"Leo 定 30min"）——与 Leo 2026-08-14 定案（`t_fast`∈[1,5) 整数默认建议 4、`t_econ`=**5 写死**、指令 5 分钟间隔 → 窗口 5 分钟两档不重叠，v5.0 §6.2.5/§8.4）**直接冲突**。S01–S19 的窗口数据排布与 manifest 期望按旧窗口 [1,5]+[6,30] 计算，在新参数下**期望结论可能不成立**。
   **动作**：对齐 `thresholds.yaml` → 重算/重排 S 系列场景数据 → 重新生成 manifest → 抽查 S01/S02/S05 人工核对。**此项完成前，manifest 只能当"三态时代快照"参考，不得当 D9 断言 oracle。**
2. **manifest 三态期望遗留**：`EXEMPT`/`SKIP` 按 §4.2 映射表消费（不改 manifest 本体，映射写在测试代码里并注明来源行）。
3. U 系列（U01–U07）按 v5.0 §8.3 已定点位（511/512 并网、521/522 退出原因）核对生成器输出——README 场景表已按此口径，重算时一并复核。
4. **`循环码非法` 分支零场景覆盖**：S12 只构造了编码脏写（`",abc."` 脏文本）一种失败，`循环码非法` 在 26 场景中没有任何数据——该类的 D9 构造用例**只能测试代码自造输入**（含义已明=0~5 循环码、越界即非法——Leo 2026-08-19 告知；轮转规律待生产数据，v5.0 §14-9）；自造用例的标注纪律见 §4.8（UNVERIFIED-ASSUMPTION）。
5. **✅ S16（`L>H` 无效窗）契约承载已定（2026-08-19 Leo 拍板）**：选 **B——`Judged` 内按档无效标记（`invalidTiers`），不并入 `Undecodable`**。理由：① 管线阶段对位——`Undecodable` = 解码失败，发生在取 `V_target` 之前；L>H 是窗口聚合**之后**才发现的数据异常（解码已成功）；② 归因纯净——`undecodable_count` 合规口径保持「解码失败归因」（编码侧的锅），采集侧脏数据不混入"谁的锅"分析；③ 粒度对齐——S16 是**按档**现象（fast 无效 + econ 正常合格）。策略层处置：与 completeness=0 同族的「判不了该档」事实。（同日补定字段可空性：VERDICT? + 不变式「为空 ⟺ 无效档」构造期强制，见 §4.8——评审指出非空枚举装不下「不可判」，随本拍板一并定；构造校验属运行时逻辑，须单测穷举 16 组合，见 §4.8 不变式构造测试。**同日交叉核对补：该档窗口整档全缺（S14）与 L>H 同走 invalidTiers**——契约空窗补全，正式版 §2.5/§2.6，S14 映射已同步 §4.2。）（历程：2026-08-19 评审自 §6-4「顺带」提级为硬前置，当日拍板，未留假绿窗口。）
