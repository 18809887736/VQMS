**核心诉求**：让"数据不可用处理策略（缺数据+解码失败）"能独立于"核心算法"解封，不互相阻塞——因为两者的解封条件本质不同（核心算法等生产数据验证，数据策略等政策口径拍板，后者理论上能更快确认）。

**结论：不需要正式插件化（多接口实现类 + Spring Bean 装配），用"参数化配置"就够。**

#### 具体怎么做

1. **核心算法保持干净**：`RegulationJudge` 只做解码 + 包络判定，遇到缺数据/解码失败时不自己拿主意，用 sealed interface/record 或类型化异常诚实报告"缺了多少、为什么解不出来"（缺失比例、失败原因分类），不吞掉信息。
2. **数据不可用策略收敛成一个纯函数 + 配置**：甲/乙/丙/丁不写成四个类，就是一个 `switch`/if 判断，行为由几个参数（阈值、剔除 vs 计不合格）决定。这些参数直接扩展你们已经验证好的 `vqms_judge_param` 模式（自建表 + CRUD + Redis 缓存），换策略 = 改配置表几行数据，代码不用动。
3. **留痕/计数用 Spring 内建事件**（可选但建议）：判定过程该上报的地方发个 `ApplicationEvent`，计数、告警各自监听，跟主逻辑物理隔离，以后加告警阈值不用碰判定代码。

#### 为什么不用插件化

四套方案本质是阈值/开关的排列组合，不是四套互不相通的算法逻辑；接口+多实现类这层抽象对你们现在的规模（团队小、场景封闭、不预期短期内新增第五种策略）是过度设计，维护成本（多写接口、Spring 装配、Bean 命名管理）大于收益。**参数化配置已经完全达成"两者解耦、各自可独立解封"这个真正目标**——因为策略数据外部化在配置表里，跟核心算法代码路径没有耦合，这才是你要的效果的关键，插件化只是达成手段之一，不是必需品。

#### 一个例外情况

如果将来丁档"挂起人工审核"这种**质变**（不是调阈值能表达的，是完全不同的处理路径）真的要落地，那时候再把参数化升级成策略模式/插件化不迟，现在没必要预留。

#### 落地建议

在确定轨加一项：**类型化失败契约 + 参数化策略骨架**——写好异常/结果类型、写好一个读配置的评估函数、复用 `vqms_judge_param` 的模式建策略参数表。这一步不依赖核心算法定稿，也不依赖政策口径拍板，现在就能开工、能编译、能用 `avc-data-gen` 的合成场景测试。等政策口径拍板后，只改配置表数值，不用动代码——跟你们 `StubRegulationJudge → DefaultRegulationJudge` 的替换范式是一致的思路。
