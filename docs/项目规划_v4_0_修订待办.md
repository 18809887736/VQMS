## A. 核心必改（4 项）

### A1. §8.2 stub 改确定性
- **位置**：§8.2（约第 319 行），`StubRegulationJudge` 描述。
- **现状**：原文「返回全 `QUALIFIED` 或**随机三态**」。
- **改为**：确定性 stub——按输入 hash 出确定结论（或固定全 QUALIFIED），并在返回里带 `stub=true` 标记。
- **原因**：随机返回让测试/集成不可复现，且会污染任何落库或缓存。注：后端 `ruoyi-vqms` 尚未落地，stub 还没真正运行，故当前是「潜在风险」而非已发生事故；改确定性仍是标准好习惯。

### A2. §8 RegulationJudge 重构为三阶段管线（最核心 · 论据已修正）
- **位置**：§8.2 接口契约（约第 305–321 行）。
- **现状**：接口 `judge(AvcCommand cmd, List<MinuteCurve> curveByMinute, JudgeParams params)` 输出 `VERDICT ∈ {QUALIFIED, PENALIZED, EXEMPT}`；§8.2（第 321 行）宣称「接口契约稳定……不破坏接口」。但**免考与门控数据在接口输入里没有通道**——算法定型要塞这两类数据时签名必然改，与「不动调用方」自相矛盾。
- **改为（三阶段管线）**：
  1. **门控前置过滤**（调用方做）：读 `yc_history` 的 AVC投退/远方就地 yx 点，排除 AVC 退出/就地模式时段的指令。**不进 judge**。
  2. **RegulationJudge 包络判定**：**从返回值移除 `EXEMPT`**，只出 `{QUALIFIED, PENALIZED}`。输入自洽，真正实现「只换实现、不动调用方」。
  3. **免考后置应用**（非判定）：**读对端 `yx501`**（全厂一个，0/1），PENALIZED + yx501=1 → 标记免考、剔除该档分母。免考判定（Q vs 极限）是对端义务，不进 VQMS judge。
- **原因（⚠️ 2026-08-14 论据修正）**：门控=前置作用域、免考=后置覆盖（草稿 §2.6 包络失败后才判），架构上不同。**原论据「免考判不了、EXEMPT 不可达」已证伪**——免考数据对端 GENERATOR 库齐全（`qYcNum`=yc217/317 逐机 Q + `GENERATOR_P_QLimit` 双向极限曲线），`docs/数据源头（草稿）.md` §4 缺口③ 已定「对端 JS 算 `yx501`、VQMS 读结论值」架构。**Leo 2026-08-14 拍板：免考判定归对端、VQMS 不背判定义务**——故 `EXEMPT` 不该是 judge（VQMS 判定接口）的输出，它是后置读 yx501 的**应用结果**，不是判定产物。
- **附带（finding A，解码归属）**：`AvcCommand` 应携带 `warn_info` 原始字段 + t₀ 实时母线电压，**解码留在 judge 实现内部**，不要让调用方预算 `V_target`（否则草稿 §2.8「循环码」位定义等解码变更会迫使调用方改动，违反「不动调用方」）。

### A3. §8.5 解码失败处理（加独立计数 + 合规确认）
- **位置**：§8.5 表格（约第 344 行），「目标值/增量解码失败 | 跳过 + 记日志，不计入发令次数」。该行在 §8.5 已标「暂定」。
- **改为**：跳过判定 + 记日志 + **单独计数 `undecodable_count` 并上报**；标注「暂定项，需与政策口径/电厂考核惯例确认」。
- **原因**：调节合格率分母=发令次数，解码失败就剔除分母=系统性抬高合格率，有合规风险。记日志留了运维痕迹但修不了分母抬高；审计看的是统计数字本身。

### A4. §12.1 D4 内联 + §10 补 API 清单
- **D4（约第 436 行）**：唯一依据「v3.4 §5.7.3 ①-a」在 v4.0 全文未复述 → **把该闸门细节（放宽边界 + 正则校验 + 解析后精确过滤）内联进 v4.0 §12.1 或新增小节**，使「无需回查 v3.4」名副其实。（D3 顺手去掉冗余的「v3.4 §5.5」引用——§13 已完整复述时间对齐规则，D3 矛盾较弱。）
- **§10（约第 395–405 行）**：现只讲前缀剥离，无端点清单 → 补 7 个前端页面所需的 `/vqms/*` 端点清单、分页/导出约定、`@PreAuthorize` perms 字符串（如 `vqms:curve:list`）。

### A5. 逻辑 FK 写路径校验（确定轨 D1~D6 开工时补）
- **位置**：§12.1 D1~D6 确定轨，`busbar`/`busbar_group`/`yc_point_map` 的维护写路径。
- **现状**：三表之间无物理外键（跨库 + RuoYi 风格，可接受），全靠应用层保证一致性。
- **改为**：关键写路径加存在性校验——维护 `busbar` 时校验 `group_num` 在 `busbar_group` 存在；维护 `yc_point_map` 时校验 `busbar_id` 存在；删除 `busbar_group` 时校验无引用。
- **原因**：无 DB 层约束 → 错漏不会报错，只会在统计结果里悄悄出错。
