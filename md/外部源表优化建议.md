# 外部源表优化建议（his_curve_sv / yc_history）

> 对象：外部只读业务源库 `10.0.0.9 / qheatavchisdb`（MySQL 5.7.44）中的 `his_curve_sv`、`yc_history` 两张表。
> 来源 DDL：[backup/his_curve_sv.sql](../backup/his_curve_sv.sql)、[backup/yc_history.sql](../backup/yc_history.sql)（Navicat 导出，仅结构）。
> 背景：VQMS 以只读方式读取这两张表做电压合格率统计；表结构由现场/源系统维护，VQMS 不直接修改。本文是**提给现场/源库 owner 的优化清单** + **VQMS 侧的反制措施**。
> 关联规划：[项目规划_v3_4.md](项目规划_v3_4.md) §4 待决第 1 条、§5.5 ⚠️、§5.7.3 ①-a。

---

## 0. 大前提：两类建议

这两张表是**外部只读源**，VQMS 不能直接 `ALTER`。建议分两类推进：

- **A 类（提给现场/源库 owner）**：改源库表结构或写入逻辑，**治本**。需现场配合。
- **B 类（VQMS 侧反制）**：不改源库也能跑稳，**兜底**。大部分已在 v3.4 规划中。

理想路径：A 类按优先级推进，B 类无论 A 类是否落地都要做（因为 B 类兜的是"DB 层静默丢数"这种连日志都没有的隐蔽故障）。

---

## 1. `his_curve_sv`（问题较重）

**现状要点**（[backup/his_curve_sv.sql:24-31](../backup/his_curve_sv.sql)）：
- `save_time varchar(255)`——时间用字符串存，**无格式约束、无时区**；
- **无主键、无任何索引**（连自增 id 都没有）；
- 每分钟双写（busbar 0/1 各一条），append-only 历史表。

这两个缺陷正是 [项目规划_v3_4.md](项目规划_v3_4.md) §4 待决第 1 条记录的"先天缺陷"。

### 1.1 A 类建议（提给现场，按优先级）

| 优先级 | 问题 | 建议改动（SQL） | 收益 |
|---|---|---|---|
| **P0** | 无索引 → 每日 rollup 范围查询**全表扫描**，历史越长越慢（"一开始无感、几个月后突然变慢"） | `ALTER TABLE his_curve_sv ADD INDEX idx_save_time (save_time);` | 范围查询从全表扫描 → 索引定位。**成本一行 SQL、收益最大**，v3.4 §4-1②(a) 已列为"优先确认项" |
| **P1** | 无主键 → InnoDB 生成隐式 6 字节 rowid，复制/归档/去重不便 | `ALTER TABLE his_curve_sv ADD COLUMN id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY FIRST;` | 有显式主键，便于精确去重与增量同步；对现有写入逻辑无影响 |
| **P1** | `save_time` 是 varchar、无格式约束 → `>= / <` 是**字符串比较**，单条脏写（如 `'2021-5-7 9:5:3'` 漏补零）会让边界行在 DB 层**静默丢失且不报错** | 用 generated 列固化成 datetime 再索引：<br>`ALTER TABLE his_curve_sv<br>  ADD COLUMN save_time_dt DATETIME(3)<br>    GENERATED ALWAYS AS<br>    (STR_TO_DATE(save_time,'%Y-%m-%d %H:%i:%s.%f')) STORED,<br>  ADD INDEX idx_save_time_dt (save_time_dt);` | 把"字符串排序恰好≈时间排序"的**数据巧合**变成**数据库保证**；脏行解析为 NULL 自动隔离，不再混入正常范围 |
| P2 | 根治：写入侧无时间格式规范 | 推动源系统写入侧强制零填充 ISO 格式（`YYYY-MM-DD HH:MM:SS[.fff]`） | 治本，但跨系统协调，周期长 |
| P3 | `average_SV decimal(10,0)` 整数位存均值，四舍五入丢 ±0.5V | 若现场重建表，建议 `decimal(12,1)` | 精度提升；当前 tolerance=300V 下不影响判定结论，非阻塞 |

> ⚠️ `high_SV` / `low_SV` 按 [项目规划_v3_4.md](项目规划_v3_4.md) §1.1 不参与合格判定（只是窗口观测极值，非阈值），其列定义**无需调整**。

### 1.2 推荐"最小改动组合"

若现场只接受一次改动，按 **P0 + P1（主键）** 两行 ALTER 即可解决"全表扫描"与"无主键"两大痛点：
```sql
ALTER TABLE his_curve_sv
  ADD COLUMN id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY FIRST,
  ADD INDEX idx_save_time (save_time);
```
若能接受 P1 的 generated datetime 列，则把索引建在 `save_time_dt` 上（语义更正确）。

## 2. `yc_history`（明显好于上一张）

**现状要点**（[backup/yc_history.sql:24-29](../backup/yc_history.sql)）：
- 已有 `UNIQUE INDEX (yc_num, yc_time)`——VQMS 的点查询 `WHERE yc_num=? AND yc_time<=? ORDER BY yc_time DESC LIMIT 1` **能走索引**；
- 但 `yc_num` / `yc_time` 均**允许 NULL**，且无显式主键；
- `yc_time` 同样是 varchar，同样有字符串范围比较隐患（但有 `yc_num` 前缀，受影响面小）。

**结论：基本够用，优先级整体低于 `his_curve_sv`。**

### 2.1 A 类建议（提给现场）

| 优先级 | 问题 | 建议改动（SQL） |
|---|---|---|
| P2 | `yc_num`/`yc_time` 允许 NULL → 唯一索引对多 NULL 不去重，脏写入会绕过去 | `ALTER TABLE yc_history MODIFY yc_num BIGINT NOT NULL, MODIFY yc_time VARCHAR(32) NOT NULL;` |
| P2 | 无显式主键（唯一索引列可空，不能当 PK） | 上一步改 NOT NULL 后，把 `(yc_num, yc_time)` 升为 `PRIMARY KEY`，或加自增 id |
| P2 | `yc_time` 是 varchar → 同 his_curve_sv 的字符串范围比较隐患 | 同 §1.1 P1 的 generated datetime 列方案 |
| P3 | `yc_data double` 浮点 | yx 开关量（0/1）/主母线号够用；若用于电压模拟量才考虑 decimal |

## 3. B 类：VQMS 侧反制（不改源库也要做）

v3.4 规划已覆盖大部分，此处汇总成落地清单：

1. **放宽边界 + 格式校验 + 解析后精确过滤**（§5.7.3 ①-a，已定）
   - SQL 边界故意放宽 ±1 天（全表无索引 → 放宽不增扫描成本），"是否属于当天"由 Java 解析后的**真实时间值**权威判断；
   - 三步：① 时间字段正则严格匹配 → 不匹配记日志（带 `stat_date` + `group_num` + 原始行）+ 标缺；② 干净行解析成真实时间 ts；③ 用 ts（不是字符串）判 `ts ∈ [stat_date, stat_date+1day)`；
   - 把"DB 层静默丢数（该取没取到，连日志都没有）"降级为"闸门可见、可记日志"的可追踪失败；顺带修复跨天 yx 阶跃在日边界被截断的问题。
2. **rollup 耗时监控**（§4-1②，待跟踪）
   - 单组单日取数 + 聚合耗时随 `his_curve_sv` 行数增长的曲线，明显上扬即启用兜底。
3. **当日返回行数计数告警**（§4-1①残留处置）
   - 预期 ≈ 组母线数 × 1440 × 采集频率；远低于预期即报警（区间阈值留待监控实现时定），兜"错位幅度超过放宽余量的恶性脏写"。
4. **兜底：自建镜像表**（§4-1②(b)，现场拒绝加索引时启用）
   - 在 VQMS 主库建 `his_curve_sv_mirror`（带主键 + save_time 索引 + datetime 列），ingestion 增量同步，把"脏乱差外部源"与"干净可查镜像"隔离。

> **残留风险（非 100% catch）**：错位幅度超过放宽余量的恶性脏写（如月位漏补零 `'2021-5-7'` 字面排序远离 `'2021-05-0x'`，±1 天捞不回）仍可能在 DB 层丢失。核心收益是 **DB 边界不再当正确性脆点**，而非保证不丢——靠调大余量（如 ±1 月）或计数告警兜底。

## 4. 若 VQMS 自建镜像表，理想结构（参考）

当现场完全不能改源库、或数据量增长导致全表扫描不可接受时，VQMS 在主库自建镜像（属 B 类第 4 项的具体设计）：

```sql
CREATE TABLE his_curve_sv_mirror (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  save_time     DATETIME(3)     NOT NULL COMMENT '解析后的真实时间(Asia/Shanghai)',
  save_time_raw VARCHAR(64)     NOT NULL COMMENT '原始字符串,留痕便于回溯脏写',
  busbar_num    BIGINT          NOT NULL,
  high_SV       DECIMAL(12,1)   DEFAULT NULL,
  low_SV        DECIMAL(12,1)   DEFAULT NULL,
  average_SV    DECIMAL(12,1)   DEFAULT NULL,
  plan_SV       DECIMAL(12,1)   DEFAULT NULL,
  fetched_at    DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_time_busbar (save_time, busbar_num),
  KEY idx_busbar_time (busbar_num, save_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='VQMS 自建:his_curve_sv 干净镜像(增量同步)';
```

设计要点：主键 + 唯一键（防重）+ 业务查询索引（按母线 + 时间）；时间双列（解析值用于查询/排序，原始值留痕）；数值列保留 1 位小数避免均值截断。

---

## 5. 一句话排序

**先向现场提 P0**（给 `his_curve_sv.save_time` 加一个普通索引）——成本一行 SQL、收益最大；**其余按 P1 → P3 推进**。无论现场配不配合，**B 类反制（尤其 §5.7.3 ①-a 三步闸门）都要落地**，因为它兜的是"DB 层静默丢数"这种连日志都没有的隐蔽故障。
